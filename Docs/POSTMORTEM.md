## 复盘一：非对称重力与三个跟手机制

**问题**：用引擎默认重力做的跳跃"飘"——上升和下降一样慢，角色像在月球上；玩家离开平台边缘后按跳没反应，落地前提前按跳也会被吞掉。

**假设**：手感差主要来自两处：① 下落段耗时与上升段相同，缺少"落地干脆"的节奏；② 输入判定只用"当前是否 grounded"这一个瞬时布尔值，没考虑人类的操作提前量。

**方案与取舍**

- 不手填重力，而是先定"跳 3 单位、0.35 秒到顶"，反推 `v0 = 2h/t ≈ 17.1`、`g_up = v0/t ≈ 49`；下落重力设 `g_down = 1.6 × g_up ≈ 78`。**取舍**：非对称重力不物理真实，但手感更好；用 `gravityScale = 0` 自己每步积分，放弃引擎自带重力。
- 土狼时间 0.12s（离开平台后仍可跳）、跳跃缓冲 0.12s（落地前按键先记下）、松键截断 0.5（松开跳键时竖直速度乘 0.5，实现可变跳跃高度）。
- **关键实现细节**：计时与意图在 `Update`，速度施加在 `FixedUpdate`；所有时间用 `deltaTime` / `fixedDeltaTime`，与帧率无关；土狼计时消费后必须清零，否则会意外二段跳。
- 落地检测用 `Physics2D.OverlapBoxAll` 并排除玩家自身的 `attachedRigidbody`；**取舍**：第一步用 Everything 掩码省去配 Layer，正式项目应改成 Ground Layer + LayerMask。

**前后数据（自己填）**

| 版本 | g_down | 到顶时间 | 总滞空 | 连跳 3 个平台成功率 | 5 人试玩"跟手"评分 |
| --- | --- | --- | --- | --- | --- |
| A | 49 | | | | |
| B | 78 | | | | |

导出方式：`JumpCurveRecorder` 按 K 生成 `jump_curve_*.csv`（jump_index, time_s, height_u），两版各跳 3 次画曲线对比。

**失败案例**：第一版把缓冲计时放在 `FixedUpdate`，低帧率下按键会被吞；改成 `Update` 采集意图、`FixedUpdate` 只施加，问题解决。此外 `Time.timeScale = 0` 的命中停顿期间 `Update` 仍会执行，跳跃缓冲计时用 `deltaTime` 会停住，属于可接受但需记录的边界。

## 复盘二：词条叠加与可复现随机

**问题**：想加 roguelite 元素，但容易做成"每加一个词条就要改一遍战斗代码"，也容易数值爆炸；联机/重开时同一 seed 却出现不同结果。

**假设**：把"效果"和"数值"彻底分开——词条只描述数据，战斗代码只读一份扁平的运行时数值；随机必须收敛到单一随机源。

**方案与取舍**

- `RunStats` 用 **struct** 而不是 class。C# 的 class 赋值是引用拷贝（有 C++ 背景最容易误判），用值类型才能保证重开一局时基础数值不被上一局词条污染。
- `Modifier` 只含 `id / displayName / target / op / value / maxStacks`；`Apply` 里一个 switch 把效果写回 `RunStats`。加新词条 = 加一条数据，战斗代码零改动。
- `maxStacks` + 射速上限 30 + 子弹数上限 5，防止乘法叠加爆炸。
- 所有随机（敌人位置抖动、三选一抽取）走同一个 `System.Random(seed)`，**绝不混用 `UnityEngine.Random`**（全局状态会破坏可复现性）。结算页显示 seed 并提供"重玩本局"。
- **取舍**：词条表先用静态代码表而非 ScriptableObject，换取最快闭环；代价是策划无法在 Inspector 里配，下一步迁移。

**前后数据（自己填）**

| 验证项 | 结果 |
| --- | --- |
| 同 seed 两次三选一选项顺序 | 一致 / 不一致 |
| 连续叠 3 层射速后 fireRate | （应 ≤ 30） |
| 叠满子弹词条后 bulletCount | （应 ≤ 5） |
| 重开后 fireRate 是否回到 6 | 是 / 否 |

**补充：随机地图与怪物**：每局生成 2~4 块悬浮平台（位置 / 宽度由 seed 决定），敌人位置在场景内随机且离玩家至少 2.5 单位；类型按 55% / 30% / 15% 分为普通（红、标准血）、快速（橙、血少射速快）、精英（紫、血厚体型大），血量、体型、颜色、射速各异。平台布局、敌人位置 / 类型 / 首发延迟、三选一抽取全部消费同一个 `System.Random(seed)`，同 seed 重玩时地图与怪物完全一致。**取舍**：用"随机布点 + 类型权重"代替程序化地牢生成，几百行代码内拿到足够重玩性；代价是房间结构固定、没有连通性保证。

**补充：玩家血量与失败结算**：`PlayerHealth` 用单例 + 0.8 秒无敌帧，敌方子弹命中扣 1 血，归零调用 `RunManager.Finish(false)` 切到「阵亡」结算。无敌帧用 `Time.time` 判断而非协程状态，避免 `timeScale = 0` 的命中停顿期间判定异常。**取舍**：敌人用定时直射而非 AI 寻路，保证玩家有可躲避的输入压力，同时不引入状态机复杂度。

**失败案例**：早期把随机抽词写成 `Random.Range`（引擎全局随机），同一 seed 两次结果不同；改为单一 `System.Random` 实例后复现。另一个坑是 `stats` 若声明为 class，`BeginRun` 里 `stats = RunStats.Base()` 会替换引用看似没问题，但任何中间持有的副本都会串味——改用 struct 后彻底消失。

## 复盘三：子弹对象池与 GC

**问题**：按住连射时，频繁 `Instantiate` / `Destroy` 子弹会在战斗高峰造成帧率抖动。

**假设**：抖动来自托管堆分配与 GC，而不是渲染。

**方案与取舍**

- `Weapon.Awake` 一次性创建 16 个子弹并全部隐藏；开火时取一个 `SetActive(true)`，命中或超时只 `SetActive(false)` 回池，运行时零分配。
- 池耗尽时**静默跳过**而不是动态扩容，保证运行时分配为零；代价是极限连射会少几发。
- 子弹不用 `Rigidbody2D`，改手动 `transform.position += dir * speed * deltaTime` + `OverlapCircleAll` 判定。**取舍**：绕开 `velocity` / `linearVelocity` 的引擎版本差异，代价是没有物理弹跳、子弹会穿过地形。

**前后数据（自己填）**：在 Profiler 里对比"每帧 Instantiate"与"对象池"两种实现，连续射击 30 秒的 GC Alloc 与帧时间 p95。

**失败案例**：池对象最初挂在玩家节点下，子弹会跟着玩家移动；改成独立的 `BulletPool` 根节点后修正。

## 复盘四：打击反馈的"预算"问题

**问题**：玩家反馈"射击时震动太强烈"。初版把屏幕震动和命中停顿绑在**每一次命中**上：0.12 单位随机跳变 + 全局 `timeScale = 0` 持续 0.05 秒。射速 6 发/秒时，等于每秒十几次地震叠加十几次卡顿。

**诊断**：不是参数太大，是**分配错了**。震动、停顿、粒子、音效都在抢玩家的注意力，而命中的频率远高于击杀和受伤。把强反馈给高频事件，结果就是强反馈失去意义、还干扰瞄准。

**方案与取舍**

- **分级**：`Hit / Kill / Hurt` 三档，震幅 0.020 / 0.045 / 0.070，时长 0.055 / 0.10 / 0.15 秒。
- **命中停顿只给低频事件**：击杀 0.035 秒、受伤 0.055 秒，普通命中完全不停顿。这是"卡"感的直接来源。
- **合并而非叠加**：0.05 秒内的连续命中，把当前抖动按衰减算到此刻的剩余幅度，再与本次取 `Max`。绝不线性相加。
- **二次衰减**：`amp = A · (remaining/total)²`，尾部收得干净。线性衰减在短时长里会显得"突然停"。
- **交给玩家**：整体乘以可持久化的「关 / 弱 / 标准 / 强」，默认弱。震屏是最主观的一项，与其争论不如给开关。

**前后对比（自己实测）**：连射 3 秒内相机位移的均方根、命中时 `timeScale` 为 0 的帧数占比、以及主观"能否稳定瞄准"。这三项比"感觉好多了"更有说服力。

**失败案例**：合并逻辑最初写成"每次命中就把结束时间往后推"，结果持续射击时抖动永不结束、幅度一直满值，比原来更晕。改成"固定窗口 + 取最大值 + 不延长时长"后才正常。

**可迁移的结论**：反馈系统该按**事件频率**分配强度预算，而不是按"这一下有多爽"。高频事件给最小可感知反馈，把强反馈留给低频高价值事件——这条在 UI 动效、音效设计里同样成立。
